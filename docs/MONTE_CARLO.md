# MONTE_CARLO — проп-симулятор и оптимизатор риска

Статус: реализовано в M1 (`src/pbl/prop/`, 2026-10-28) · отличия от текста — §14

Документ — спецификация ядра. Всё, что помечено `[предложено]`, — рабочее допущение до ОК Nikita ([DECISIONS](DECISIONS.md#ждут-ок)). Всё, что помечено `[открыто]`, — неизвестный факт о правилах; симулятор считает оба варианта или консервативный.

## 1. Назначение

На входе — сделки стратегии (OOS / walk-forward или демо) и профиль пропа. На выходе — для каждой пары стратегия × программа: вероятности по фазам, `P(funded)`, `P(1-я выплата)`, дни до funded, причины провалов, оптимальный риск по фазам, EV на взнос и рекомендация (§9).

Принципы:
- Решения — только по OOS / WF и демо. MC на in-sample — справка с пометкой `IN-SAMPLE`.
- Дневная просадка — по **внутридневной эквити**, а не по закрытым сделкам.
- Предохранители бота (дневной 50%, общий 60%) — часть модели, не отключаются. Расчёт «без предохранителей» — только для сравнения.
- Неясное правило → консервативный вариант + пометка.

### Обозначения

| Символ | Смысл |
|---|---|
| `B0` | начальный баланс аккаунта (каждая фаза и funded — новый аккаунт с `B0`) |
| `B_t`, `E_t` | баланс (закрытые) и эквити (с плавающими) в момент `t` |
| `B_SOD`, `E_SOD` | баланс и эквити на начало торгового дня по серверу фирмы |
| `f` | риск на сделку, доля `B0` (например 0.008 = 0.8%) |
| `κ` | поправка округления лота: фактический риск / номинальный |
| `R` | результат сделки в единицах номинального риска |
| `τ_p`, `m_p` | цель и минимум торговых дней фазы `p` |
| `p_DL`, `p_ML` | дневной и общий лимит, доля `B0` |
| `γ_D`, `γ_T` | доли предохранителей бота: 0.5 (макс. 0.7) и 0.6 |
| `N` | число путей MC, ≥ 10 000 |

## 2. Входные данные

### 2.1 Сделка

Одна строка `trades.parquet` от движка. Издержки уже внутри `R`, поэтому `R` не зависит от объёма (спред, комиссия за лот, своп и проскальзывание растут линейно с лотом).

| Поле | Тип | Смысл |
|---|---|---|
| `trade_id`, `strategy_id`, `variant_id` | str | идентификаторы |
| `symbol`, `side` | str | инструмент, long/short |
| `open_utc`, `close_utc` | datetime | время, UTC |
| `entry`, `exit`, `sl`, `tp` | float | цены; `sl` обязателен |
| `stop_dist` | float | `|entry − sl|` в пунктах |
| `point_value` | float | стоимость пункта на 1 лот в $ на момент входа |
| `r_gross` | float | результат до издержек, R |
| `cost_spread_r`, `cost_comm_r`, `cost_swap_r`, `cost_slip_r` | float | издержки по статьям, R |
| `r_net` | float | `r_gross − Σ cost_*` |
| `mae_r`, `mfe_r` | float | худший и лучший плавающий результат, R |
| `hold_sec` | int | удержание |
| `exit_reason` | enum | sl, tp, trail, be, partial, time, guard, friday_close, eod |
| `news_flag` | bool | вход или выход в окне новостей фирмы |
| `mods` | int | число модификаций ордера (для лимита 2 000 сообщений) |
| `sample` | enum | IS, WF, HOLDOUT, DEMO |

Плюс `equity_R.parquet`: поминутная плавающая прибыль каждой открытой сделки в R по худшей цене минуты (лонг — low по bid, шорт — high по ask).

### 2.2 Дневная запись

Строится из сделок и поминутной эквити **под профиль фирмы**: день = `[00:00, 24:00)` по серверу этой фирмы. Все величины в R при номинальном риске 1R на сделку.

| Поле | Смысл |
|---|---|
| `date`, `weekday`, `year` | серверная дата |
| `n_opened` | сделок открыто; торговый день, если ≥ 1 `[открыто: что FN считает торговым днём]` |
| `c_in`, `c_out` | плавающий результат перенесённых позиций на начало и конец дня |
| `db` | изменение баланса за день (закрытые сделки) |
| `b_max` | максимум накопленного закрытого результата внутри дня |
| `path` | внутридневной путь эквити относительно `E_SOD`, сжатый зигзагом (см. ниже) |
| `risk_open_max` | максимум суммарного открытого номинального риска, в единицах «сделок по 1R» |
| `news_pos_r` | прибыль сделок с `news_flag` |
| `cost_*_r` | издержки дня по статьям |
| `trades` | ссылки на сделки дня (`stop_dist × point_value` для расчёта лотов) |

**Сжатие пути.** Поминутный путь `v(t)` хранится как зигзаг: сохраняются все локальные экстремумы с размахом ≥ `ε` (по умолчанию `ε = 0.02R`) плюс первая и последняя точка. Любое пропущенное колебание меньше `ε`, поэтому проверка нижних барьеров идёт по `v_k − ε`, верхних — по `v_k` (консервативно). Зигзаг сохраняет порядок событий, поэтому по нему однозначно определяется, какой барьер задет первым, в том числе для трейлинга от пика эквити. Если две проверки дают противоположные события в одной точке — считаем худшее (как правило «стоп и тейк в одном баре — стоп»).

### 2.3 Профиль пропа

Поля схемы `Program` (pydantic, T2). Каждая программа — набор фаз и правил счёта:

| Группа | Параметры |
|---|---|

| Фазы | список `{target_pct, min_days, max_days}`; funded — отдельная фаза без цели |
| Дневной лимит | `pct`, `reference ∈ {sod_balance, max_sod_balance_equity}`, `amount_basis ∈ {initial, reference}`, `check ∈ {realtime_equity, eod}`, `reset` + `server_tz_rule` |
| Общий лимит | `type ∈ {static, trailing}`, `pct` или `abs`, `trail_source ∈ {balance_eod, balance_realtime, equity_realtime}`, `lock_level`, `lock_trigger`, `check ∈ {realtime_equity, eod_balance}` |
| Funded | `payout`: `first_after_days`, `cycle_days`, `min_profit`, `split`, `consistency_best_day_max`, `profitable_days_rule`, `refund_on_payout_k`; `risk_rule_max_open_pct`, `news_profit_factor`, `striking` |

### 2.4 Схема риска

| Параметр | Смысл | По умолчанию |
|---|---|---|
| `f_p` | риск на сделку по фазам (Ф1, Ф2, Ф3, funded), доля `B0` | из оптимизатора (§10) |
| `γ_D` | внутренний дневной стоп, доля дневного лимита | 0.5 (≤ 0.7) |
| `γ_T` | внутренний общий стоп, доля общего лимита | 0.6 |
| `flatten_at_target` | закрыть всё при достижении цели (+ буфер 0.1% `B0`) | да |
| `after_target` | если цель есть, а мин. дней нет: торговать с `f_min` | `f_min` = мин. лот `[предложено]` |
| `R1` | снижение риска при просадке фазы ≥ `x`% общего лимита: `f ← k·f` | `x ∈ {нет, 30, 50}`, `k = 0.5` |
| `R2` | «последняя миля»: если до цели меньше одного среднего профита, `f ← max(f_min, остаток / (B0 · r̄_win))` | вкл/выкл |
| `guard_slip` | проскальзывание при закрытии по предохранителю | 0.1R при текущем `f` `[предложено]` |

Изменения риска (R1, R2) применяются со следующего торгового дня; предохранители и цель срабатывают внутри дня по пути.

## 3. Модель счёта

### 3.1 Объём и округление лота

Для сделки `i` при риске `f`:

$$
\text{lots}_i = \max\!\Big(\text{min\_lot},\ \Big\lfloor \frac{f B_0}{d_i V_i \cdot \text{step}} \Big\rfloor \text{step}\Big),\qquad
\kappa_i = \frac{\text{lots}_i\, d_i V_i}{f B_0}
$$

`d_i` — `stop_dist`, `V_i` — `point_value`. Объём также ограничен маржой: `lots · contract · price ≤ leverage · E`. Для дня берём `κ_d = max_i κ_i` (консервативно для убытков). Если `κ_i > 1.5` у более чем 5% сделок — кандидат риска **недопустим** для этого размера счёта (слишком маленький счёт для таких стопов).

### 3.2 Пересчёт дня

Для дневной записи `d` при риске `f` и масштабе `s_d = f κ_d B0`:

- эквити в момент `t` пути: `E_t = B_SOD + s_d (c_in + v(t))`
- конец дня без событий: `B_EOD = B_SOD + s_d · db`, `E_EOD = B_EOD + s_d · c_out`
- максимум баланса внутри дня: `B_SOD + s_d · b_max`

Перенос позиций через ночь между случайно склеенными днями даёт разрыв эквити на стыке. Это допущение; для внутридневных стратегий его вклад нулевой, для остальных — показываем долю дней с `c_in ≠ 0`.

### 3.3 Дневной лимит

Уровень пробоя на день `d` (пробой, если `E_t < L_D`; равенство — не пробой):

| Вариант | Формула | Где |
|---|---|---|
| От баланса на начало дня | `L_D = B_SOD − p_DL · B0` | FundedNext (пример фирмы: на $100K при +$2 000 за день лимит $7 000 = тот же уровень `B_SOD − 5%·B0`) |
| От большего из баланса и эквити | `ref = max(B_SOD, E_SOD)`, `L_D = ref − p_DL · min(B0, ref)` | FundingPips; `min` — консервативно, пока не известна база суммы `[открыто]` |
| Нет дневного лимита | — | FN Instant |

Проверка — по эквити в реальном времени (плавающие, свопы и комиссии входят).

### 3.4 Общий лимит

| Тип | Уровень пробоя `L_M(t)` | Проверка |
|---|---|---|
| Статичный | `B0 (1 − p_ML)` | эквити в реальном времени |
| Трейлинг по балансу (realtime) | `min(H_B − D, Lock)`, `H_B` — максимум баланса | эквити; внутри дня берём `H_B` уже с учётом `b_max` (консервативно) |
| EOD-трейлинг | `min(H_EOD − D, Lock)`, `H_EOD = max(B0, max_{j<d} B_EOD,j)` — пересчёт только в конце дня | эквити в реальном времени против уровня, зафиксированного на начало дня |
| Трейлинг по эквити (intraday) | `min(M_t − D, Lock)`, `M_t` — максимум эквити, включая плавающую прибыль | по зигзагу пути |

`D` — дистанция (доля `B0` или $). `Lock` — уровень, выше которого трейлинг не поднимается (обычно `B0`, иногда `B0 + x`); `lock_trigger` — когда фиксируется (FP Zero: после +5%). После фиксации уровень больше не двигается. Поведение уровня после выплаты — параметр `payout_floor_behavior` `[открыто для FN Instant]`.

### 3.5 Предохранители бота

| Предохранитель | Уровень | Действие |
|---|---|---|
| Дневной | `G_D = ref − γ_D · A`, где `A` — сумма дневного лимита; если у программы нет дневного лимита — `A = D` (дистанция общего) `[предложено]` | закрыть всё по `G_D − guard_slip`, до конца дня не торговать |
| Общий | статичный: `G_T = B0 − γ_T · p_ML · B0`; трейлинг: `G_T = L_M + (1 − γ_T) · D` | закрыть всё, бот стоп → путь заканчивается с причиной `guard_total` |

Пробой лимита фирмы при живом предохранителе возможен только при скачке цены (гэп, минута с резким ходом): если точка пути сразу ниже `L_D` или `L_M`, это пробой. Так MC честно показывает гэповый риск.

### 3.6 Порядок проверок внутри дня

Проходим точки зигзага по времени; в каждой точке:

1. Пробой лимита фирмы (`L_D`, `L_M`) по `v_k − ε` → провал фазы (`daily` / `max`).
2. Предохранители (`G_D`, `G_T`) → закрытие по уровню минус `guard_slip`; если после проскальзывания ниже лимита фирмы → провал.
3. Цель: `E_t ≥ B0 (1 + τ_p) + буфер` и `flatten_at_target` → закрыть всё; цель достигнута.

Если в одной точке выполняются и п.1–2, и п.3 — считаем худшее.

В конце дня: обновить `B`, `H_EOD`, `H_B`, счётчик торговых дней (`n_opened ≥ 1`), проверить EOD-правила.

### 3.7 Фазы, сроки, неактивность

- Фаза пройдена, когда цель достигнута **и** торговых дней ≥ `m_p`. Если цель есть, а дней нет — `after_target` (торговля с `f_min`, лимиты по-прежнему действуют).
- Следующая фаза — новый аккаунт с `B0`, сброс всех уровней. Пауза на проверку между фазами — 2 календарных дня `[предложено]` (влияет только на сроки).
- `max_days` фазы (если есть) → провал `timeout`.
- **Горизонт.** У FN и FP срока нет, но путь ограничен: 365 календарных дней от покупки до первой выплаты `[предложено]`. Не успел — `timeout`.
- **Неактивность.** Нет торгового дня дольше `inactivity_days` календарных → провал `inactivity` (FN 60 `[открыто: только со скриншота]`, FP 30).

### 3.8 Funded и первая выплата

- Отсчёт выплат — с первой сделки на funded `[предложено: консервативно]`.
- Проверка выплаты — только в дни цикла (`first_after_days`, затем каждые `cycle_days`), а не в любой день после `[предложено: консервативно]`.
- Выплата возможна, если прибыль ≥ `min_profit` (по умолчанию 1% `B0` `[открыто]`) и выполнены условия варианта выплат (consistency, прибыльные дни).
- Сумма: `Π = split × (B − B0 − 0.6 · news_pos)` для FN funded (прибыль в окне новостей засчитывается на 40%); для FP прибыль новостных сделок вычитается полностью.
- После выплаты баланс возвращается к `B0`; трейлинг-уровень — по `payout_floor_behavior`.
- **Risk Rule FN** (funded и Instant): `f · κ · risk_open_max ≤ 3%` в любой день. Оптимизатор держит это ограничение (§10); если нарушено — провал `rule` (консервативно, у фирмы первое нарушение — предупреждение и минус прибыль).
- **FP Striking** (funded > $25K, 1-Step Flex): плавающий убыток одной идеи > 1.2% (1-Step — 1%) → ограничение `f · κ · (1 + max_slip) < 1.2%`.
- **Consistency** — условие выплаты, а не провал: если не выполнено, выплата переносится на следующий цикл.

Причины провалов (взаимоисключающие, по первому событию): `daily`, `max`, `guard_total`, `timeout`, `inactivity`, `rule`.

## 5. Бутстрэп

- **Единица** — дневная запись, включая дни без сделок (сохраняет частоту торговли и паузы).
- **Схема** — stationary bootstrap (Politis, Romano 1994), циклический: старт с равновероятного дня, дальше следующий день с вероятностью `1 − 1/L`, иначе прыжок на новый случайный старт.
- **Длина блока** `L` — автоматически по Politis, White (2004) на дневном R, в пределах [3, 20] дней `[предложено]`.
- **Календарь** — свой у каждого пути: торговые дни Пн–Пт, после пятницы +2 календарных дня. По нему считаются выплаты, неактивность и горизонт. Праздники не моделируем.
- **Общие случайные числа (CRN)** — одинаковые индексы дней для всех программ, кандидатов риска и стрессов при одном seed. Разница между вариантами тогда — от правил, а не от шума.
- Предупреждение `МАЛО ДАННЫХ`, если на входе < 250 торговых дней или < 100 сделок.

## 6. Стрессы

Все стрессы, кроме «худших лет», — преобразования **списка сделок** до построения дневных записей. Так путь эквити остаётся согласованным со сделками.

| Стресс | Преобразование |
|---|---|
| Базовый | как есть |
| Худшие годы | бутстрэп только из двух худших календарных лет по чистому R (или худшего 12-месячного окна, если лет < 4) |
| Издержки × 1.5 и × 2 | спред и проскальзывание × m: `r' = r_net − (m − 1)(cost_spread_r + cost_slip_r)`; путь сделки сдвигается на ту же величину с момента входа; `guard_slip × 3` |
| Пропуск сделок | каждая сделка удаляется с вероятностью 10%; 20 повторов набора с разным seed |
| Винрейт −5 п.п. и −10 п.п. | `k = round(δ · n)` случайных прибыльных сделок становятся убыточными: `r_net` берётся из эмпирического распределения убытков, путь — `min(исходный путь, линейная интерполяция от 0 до нового r_net)` |
| Пакет | издержки × 1.5 + винрейт −5 п.п. + пропуск 10% |

В отчёте — `P(1-я выплата)` и EV₁ по каждому стрессу при риске, найденном на базовом сценарии.

## 7. Неопределённость и доверительные интервалы

Две разные неопределённости — показываем обе.

1. **Шум MC.** Интервал Уилсона для доли `P̂` при `N` путях:
$$
\frac{\hat p + \frac{z^2}{2N} \pm z\sqrt{\frac{\hat p(1-\hat p)}{N} + \frac{z^2}{4N^2}}}{1 + \frac{z^2}{N}},\qquad z = 1.96
$$
При `N = 10 000` это около ±1 п.п.

2. **Конечная выборка сделок** — главная. Внешний бутстрэп: `B = 200` псевдо-историй той же длины (тот же stationary bootstrap по дням), на каждой — MC на 2 000 путей. Интервал — 5-й и 95-й перцентили `P` по псевдо-историям.

Формат: `P(1-я выплата) = 41% (MC ±1 п.п.; по выборке 28–55%)`. Медиана и p90 дней — с теми же интервалами.

## 8. EV на взнос

Бюджет на взносы не задан, поэтому считаем на **одну покупку** по цене программы.

**EV₁ — только первая выплата (гейт S3) `[предложено]`:**

$$
\mathrm{EV}_1 = -C + P_1\Big(\mathbb{E}[\,s\,\Pi_1 \mid \text{выплата}\,] + \text{Refund}_1\Big)
$$

- `C = fee + addons` (EA Add-On $5; add-on «No Min Days», если используется).
- `P_1 = P(1-я выплата)`, `s` — доля трейдера, `Π_1` — прибыль на дату первой выплаты (после правил новостей).
- `Refund_1 = fee`, если взнос возвращается с первой выплатой (FN 2-Step), иначе 0.

**Точка безубыточности:** `P* = C / (E[s Π_1] + Refund_1)`.

> Пример арифметики (не результат): FN 2-Step $25K, `C = 199.99 + 5 = 204.99`, средняя прибыль к первой выплате 3% = $750, `s = 0.8` → `E[sΠ_1] = 600`, `Refund_1 = 199.99`. Тогда `P* = 204.99 / 799.99 ≈ 25.6%`, и при `P_1 = 35%` `EV₁ ≈ −204.99 + 0.35 · 799.99 ≈ +$75`.

**EV₁₈₀ — горизонт 180 дней от покупки (справка) `[предложено]`:** сумма ожидаемых выплат за горизонт плюс возврат взноса, если до выплаты с возвратом дошли, минус `C`. Учитывает программы с поздним возвратом (FN 1-Step и Lite — с 3-й выплатой, FP — с 4-й).

**Дополнительно:** ожидаемое число попыток до первой выплаты `1 / P_1`, ожидаемые траты `C / P_1`, ожидаемое время с учётом повторов `E[T_усп] + (1/P_1 − 1) · E[T_провал]`.

## 10. Оптимизатор риска по фазам

**Цель:** максимум `P(1-я выплата)` при `EV₁ > 0`.

**Переменные:** `f_1, f_2, (f_3), f_F` и правила `R1`, `R2`. Сетка `f`: 0.25, 0.5, 0.75, 1.0, 1.25, 1.5, 2.0, 2.5, 3.0% `B0` `[предложено]`.

**Ограничения:**

| # | Ограничение |
|---|---|
| C1 | Risk Rule FN: `f_F · κ · risk_open_max ≤ 3%` во всех днях выборки (и `f` Instant так же) |
| C2 | FP Striking: `f_F · κ · (1 + max_slip) < 1.2%` (1-Step Flex — 1%) |
| C3 | Мин. лот: `κ_i ≤ 1.5` у ≥ 95% сделок |
| C4 | Маржа: объём в пределах плеча фазы |

**Поиск:**

1. **Раздельно по фазам** (фазы — независимые аккаунты): для каждой фазы `P(пройти)` (для funded — `P(выплата | funded)`) по сетке, 2 000 путей, CRN.
2. **Совместно**: покоординатный спуск по `(f_1, f_2, f_F, R1, R2)` от точки шага 1 на полном MC, 2 000 путей, CRN, два прохода.
3. **Переоценка**: топ-5 кандидатов — 10 000 путей на **новом** seed (против «проклятия победителя»).
4. **Устойчивый выбор**: берём кандидат с **наименьшим риском**, чья `P` не ниже максимума больше чем на `max(1 п.п., полуширина CI шума MC)` `[предложено]`.

**Выход:** риск по фазам, включённые правила, кривая `P(f)` по каждой фазе (для графика «риск по фазам» в Prop simulator).

Подбор риска — тоже выбор на тех же OOS-данных, поэтому итоговая `P` слегка оптимистична. Шаги 3–4 и внешний бутстрэп (§7) это ограничивают; в отчёте пишем, что риск подобран.

## 11. Портфель на одном аккаунте

- Дневные записи нескольких стратегий объединяются **по календарной дате** (одинаковые границы дня фирмы); бутстрэп выбирает даты целиком — корреляции между стратегиями сохраняются.
- Путь дня строится из суммы поминутных эквити стратегий с весами `w_s` (доля риска каждой). Веса — небольшая сетка; для каждой точки записи пересобираются (дёшево по сравнению с MC).
- Ограничения: суммарный `risk_open_max` с весами ≤ 3% (FN Risk Rule), лимит сделок и сообщений в день на аккаунт.
- FN «distinct strategy»: портфель живёт на одном аккаунте; одна и та же стратегия на двух аккаунтах FN — запрещено.

## 12. Проверка симулятора

Выгрузки сделок нет, поэтому симулятор проверяется на синтетике и эталонах.

| # | Тест | Критерий |
|---|---|---|
| V1 | Задача о разорении: i.i.d. сделки ±1R, одна в день, без дневного лимита, нижний барьер `−a`, цель `+b` | `P(цель) = (1 − (q/p)^a) / (1 − (q/p)^{a+b})` при `p ≠ q`, `a / (a+b)` при `p = q`; MC в 99% интервале Уилсона |
| V2 | Длительность при `p = q` | `E[T] = a·b` сделок, MC в 99% интервале |
| V3 | Детерминированные последовательности на каждое правило | пробой ровно на границе (`E = L` — не пробой, `E < L` — пробой), цель, мин. дни, EOD vs intraday трейлинг, lock, сброс дня по серверу, переход на летнее время |
| V4 | Свойства (hypothesis) | выше цель → P не выше; шире лимит → P не ниже; выше издержки → P не выше; `P(1-я выплата) ≤ P(funded) ≤ P(Ф1)`; одинаковый seed → одинаковый результат |
| V5 | Две реализации | медленная эталонная на чистом Python и numba-ядро дают **идентичный** результат на 200 путях с одним seed |
| V6 | Эталонные стратегии | «монетка» с издержками → EV₁ < 0 во всех программах; синтетика с известным перевесом → P растёт с перевесом |
| V7 | Предохранители | гэп через `G_D` и `L_D` в одной минуте → пробой фирмы; плавный путь → закрытие по `G_D − guard_slip` |

- `numpy.random.SeedSequence(seed).spawn(...)` — отдельные потоки на программу, стресс и внешний бутстрэп; CRN внутри одного сравнения.
